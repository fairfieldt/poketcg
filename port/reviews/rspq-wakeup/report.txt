The shipped SDK predates an upstream ares queue-wakeup fix.

The reported PC 0x018 is immediately after the ordinary BREAK in RSPQCmd_WaitNewInput, the queue engine's empty-input sleep loop. Status 0x7003 records HALT/BROKE and normal queue signals 5, 6 and 7; signal 7 means more input has been announced. Signals 3 and 4, high-priority running/requested, are absent. The RDP is ready with current=end and no busy flags. The last-loaded RDP overlay is not evidence that its drawing code asserted. These values were captured before the crash handler forcibly halts the processors.

The old rspq_flush_internal writes a wakeup, waits ten NOPs, and writes it again. Upstream commit cd5b8f567006 documents that ares JIT scheduling can miss both wakeups because the CPU and RSP do not interleave at the assumed instruction boundaries. Its targeted workaround inserts a branch among those NOPs. The project-local backport changes only that assembly statement, preserving the SDK, microcode, queue ABI and timeout checks. The installed SDK is untouched.

The project checks copied source/private-header hashes, the patched C hash, seven public headers, and the installed queue microcode's stable allocated sections and nine exported endpoints. Fifteen positive/negative guard tests pass, including detection under Python -O. A separate same-layout negative control replaces only the compiled branch instruction with NOP, leaving all data, symbols and other code unchanged.

The later high-priority REQUESTED-clear race fix and atomic low-priority handoff fix are kept separate. The former's typical retained high-priority signal is absent in this screenshot. Neither is silently bundled into this candidate.

Native validation:
- Wake-only candidate resumed the actual byte-verified Jennifer journal for 2,002 completed frames, 112 requests, through turn 7, with the real mixer/RDP/SRAM and no timeout, assertion or engine error. A test-only driver supplies ACKs and normal action choices.
- The original bounded exact-duel fixture reached 3,777 frames without a timeout, but started with an empty journal. It is not presented as a fully controlled real-journal A/B.
- Original SDK, same-layout NOP control, and wake-only fixed queue all passed 4,096 ordered callbacks, varied normal/high-priority buffer wraps, and idle wakeups.
- The optional forced-window probe is inconclusive: ares does not honor the required one-instruction SP single-step, so both builds fail its PC0x008 setup precondition. It does not evaluate the fix and is not counted as a candidate failure.

The original intermittent user timeout was not reproduced. This hotfix backports the upstream ares workaround matching the observed sleep/wakeup signature, with regression soaks and unchanged timeout detection; it is not claimed as a demonstrated reproduction-and-elimination of that exact occurrence. Runtime hotfix commit: 4d0b4a50.
